# TableCommandPlanner.applyCommandsToCore

## Declaration

```typescript
public applyCommandsToCore(cmds: TableCommand[]): void
```

## Purpose

Use `applyCommandsToCore()` as the single application channel for externally authored command batches: it applies `cmds` to the planner's core `TableState` through the exact same interpreter the planner uses for its own auto-advance, so all subsequent planning decisions (`insertRow`, `deleteRow`, `merge`, `unmerge`, `forEachMainMergedCell`) are made from a state that includes the external batch.

The key mental model: the planner and any `BuildinStateInterpreter` you create share the **same** core `TableState` — there is exactly one state. A batch must therefore be applied **exactly once**:

- If the external module already applied its batch to the same core instance itself, the planner already sees it — there is nothing to sync, and feeding the batch again would double-apply it
- If the batch exists but has not been applied to the planner's core (an archived batch being replayed, a batch authored by a peer planner over its own state), `applyCommandsToCore()` is how you apply it

**When to use:**

- Applying an externally authored batch (hand-built commands, a peer planner's batch, an archived/replayed sequence) to the planner's core
- Continuing to plan on the same planner right after an external batch joined the state

**When NOT to use:**

- The batch was already applied to the same core instance by the external module — the state is current; feeding it again double-applies (structural commands shift twice)
- Batches generated by this planner's own methods — the mirror already advanced during generation; feeding them back applies them a second time
- Batches that were never applied anywhere and should stay that way — `applyCommandsToCore()` applies them for real

## Parameters

### `cmds: TableCommand[]` (required)

The externally authored command batch to apply.

**Valid values:**

- Any valid `TableCommand[]`, including structural commands (`INSERT_ROW`, `DELETE_ROW`, `INSERT_COL`, `DELETE_COL`) and cell commands (`SET_CELL_ATTR`, `CLEAR_CELL_ATTR`)
- An empty array is a no-op

**Behavior:**

- Commands are applied through the planner's internal interpreter with semantics identical to `BuildinStateInterpreter.applyCommands()`
- The batch is applied to the core only — it is never appended to the generated-command buffer, so `getCommands()` and `getNewCommandsAndReset()` output is unaffected
- Structural commands shift existing merges like any application does: an `INSERT_ROW` at index 0 moves existing merge main cells down; a `DELETE_ROW` above a merge moves it up

## Return Value

Returns `void`.

The meaningful effect is on state: the core `TableState` now reflects the fed batch, and later planner operations generate commands consistent with the updated layout.

## Semantics Detail

### One batch, one application

The failure mode to stay aware of is double application. Because `SET_CELL_ATTR` is idempotent, feeding a merge batch twice looks harmless (same values written twice) — but structural commands are not: feeding `INSERT_ROW` twice grows the table twice.

**Boundary to keep in mind:** applying a hand-built merge batch via your own `BuildinStateInterpreter` _and_ via `applyCommandsToCore()` on the same table leaves merge spans looking correct (idempotent SETs) while a later-fed `INSERT_ROW` reveals the double shift. Choose one channel per batch:

- **Shared state, external module applies directly** — plan immediately; no feed
- **Batch not yet on the planner's core** — feed it via `applyCommandsToCore()`; that application counts

### Same interpreter as auto-advance

Every planner method (e.g. `merge()`) ends by applying its newly generated commands through the internal interpreter. `applyCommandsToCore()` uses that same interpreter, so an external batch and a planner-generated batch leave the state in exactly the same kind of shape.

## Best Practices

1. **Feed exactly once**
   - Track who applies what: either the external module applies to the shared core (then skip the feed), or the planner applies via `applyCommandsToCore()` (then the external module must not also apply)
   - For replay pipelines this is natural: apply the archived batch once, through `applyCommandsToCore()`, and continue planning

2. **Feed before the next planner decision**
   - External batch joined the state + planner decision = correct results only if the feed happened first
   - A typical symptom of a missing feed: `unmerge()` on an externally created merge generates nothing, or `insertRow()` ignores it

3. **Keep the buffer contract in mind**
   - Fed batches never appear in `getCommands()` / `getNewCommandsAndReset()` — those represent planner-generated commands only, which is what replay/undo pipelines record

## Common Pitfalls

1. **Applying the batch through two channels**

   ```typescript
   // BAD: interpreter.applyCommands mutates the same core the planner reads
   interpreter.applyCommands(externalMerge) // First application
   planner.applyCommandsToCore(externalMerge) // Second application (hidden for SETs,
   // revealed later by structural commands)

   // GOOD: one channel per batch
   planner.applyCommandsToCore(externalMerge) // The only application
   ```

2. **Feeding planner-generated commands back**

   ```typescript
   // BAD: the planner already applied these during generation
   const cmds = planner.merge(0, 0, 1, 1)!
   planner.applyCommandsToCore(cmds) // Applies the merge a second time

   // GOOD: only feed batches authored outside the planner
   planner.applyCommandsToCore(handBuiltBatch())
   ```

3. **Expecting the batch in `getCommands()`**

   ```typescript
   // BAD: assumes fed commands are recorded
   planner.applyCommandsToCore(external)
   const all = planner.getCommands() // Does NOT contain `external`

   // GOOD: treat the buffer as planner-generated commands only
   planner.applyCommandsToCore(external)
   const next = planner.unmerge(1, 1) // Buffer contains only these
   ```

4. **Skipping the feed when the batch never reached the core**

   ```typescript
   // BAD: merge created on a peer table copy, local planner never told
   const cmds = peerPlanner.merge(1, 1, 2, 2) // Applied on the peer's state only
   localPlanner.insertRow(2) // Decisions made without knowing about the merge

   // GOOD: replay the batch into the local planner's core first
   localPlanner.applyCommandsToCore(cmds)
   localPlanner.insertRow(2) // rowSpan adjustment now sees the merge
   ```

## Complete Example

```typescript
import {
  TableState,
  TableCommandPlanner,
  type TableCommand,
} from '@aptx/table-commands-generator'

// Setup
const table = new TableState(5, 5)
const planner = new TableCommandPlanner(table)

// Scenario 1: Apply an externally hand-built merge batch through the planner
const externalMerge: TableCommand[] = [
  { type: 'SET_CELL_ATTR', row: 1, col: 1, attr: 'rowSpan', value: 2 },
  { type: 'SET_CELL_ATTR', row: 1, col: 1, attr: 'colSpan', value: 2 },
  {
    type: 'SET_CELL_ATTR',
    row: 1,
    col: 2,
    attr: 'isMergedPlaceholder',
    value: true,
  },
  {
    type: 'SET_CELL_ATTR',
    row: 2,
    col: 1,
    attr: 'isMergedPlaceholder',
    value: true,
  },
  {
    type: 'SET_CELL_ATTR',
    row: 2,
    col: 2,
    attr: 'isMergedPlaceholder',
    value: true,
  },
]

// The feed IS the application - do not also apply it via another interpreter
planner.applyCommandsToCore(externalMerge)

// Planner decisions are now made from the merged layout:
const merges: Array<{
  row: number
  col: number
  rowSpan: number
  colSpan: number
}> = []
planner.forEachMainMergedCell((info) => merges.push(info))
console.log(merges) // [{ row: 1, col: 1, rowSpan: 2, colSpan: 2 }]

// Scenario 2: Subsequent planning sees the fed merge
const unmergeCmds = planner.unmerge(1, 1)
console.log(unmergeCmds!.length) // 5 clear commands for the fed merge
console.log(planner.getCommands()) // Contains only the unmerge batch, not `externalMerge`

// Scenario 3: External structural command shifts the state
planner.getNewCommandsAndReset() // Take the unmerge batch out of the buffer

// A row inserted above all merges shifts them down (feed = the one application)
planner.applyCommandsToCore([{ type: 'INSERT_ROW', index: 0, count: 1 }])
console.log(table.getRowCount()) // 6

// Planning continues against the shifted layout
const insertCmds = planner.insertRow(3)
console.log(insertCmds![0]) // { type: 'INSERT_ROW', index: 3, count: 1 }

// Scenario 4: Replaying an archived batch onto the same planner
function replayAndContinue(
  planner: TableCommandPlanner,
  archived: TableCommand[],
): void {
  planner.applyCommandsToCore(archived) // The one application of the batch
  // ... planner is now safe to use for further edits
}

// Scenario 5: The double-application footgun (demonstration, not usage)
const before = table.getRowCount()
planner.applyCommandsToCore([{ type: 'INSERT_ROW', index: 0, count: 1 }])
planner.applyCommandsToCore([{ type: 'INSERT_ROW', index: 0, count: 1 }])
console.log(table.getRowCount() - before) // 2 - the same batch applied twice
```

## Related APIs

- `TableCommandPlanner.getNewCommandsAndReset()` - Take planner-generated commands out of the buffer (external batches never enter it)
- `TableCommandPlanner.forEachMainMergedCell()` - Read back the merge layout after feeding
- `BuildinStateInterpreter.applyCommands()` - The interpreter semantics `applyCommandsToCore()` reuses
